# 技术不足之处与待办清单

> 用途：汇报参考 / 项目跟进 / 上线前扫尾。
> 说明：本文件只做现状梳理与规划，**不涉及任何代码改动**。
> 最后核对时间：2026-08-18。测试数、表结构、后台功能均以当前代码为准。

---

## 一、技术不足之处（按优先级）

### 🔴 P0 · AI 功能尚无每日额度限制（代码侧最高优先级）

- **现象**：AI 相关接口（AI 导师 `/api/tutor/chat`、能力分析 `/api/assessment/analyze`、课程推荐 `/api/recommend/courses`、实操分析 `/api/practice/analyze`）目前**对任何使用者都不设每日调用上限**——未缴押金、免费试用期内的用户，AI 都能无限调用。
- **根因**：这些接口**没有读取当前用户身份**（无 `Depends(get_current_user)` / `get_optional_user`），自然无法按用户做限额。
- **目标**：未缴押金或仍在试用期的用户，AI 每天设置一个使用上限（如每天 N 次）；缴了押金的用户放开。
- **待办（建议分两步）**：
  1. 让 AI 接口识别当前用户（接入鉴权）
  2. 新增"每日 AI 次数"记录表 + 按押金状态限流
- **注意**：这是当前**唯一明确的代码侧短板**，汇报时作为最高优先级待办，承诺"这几天改完"。

### 🟠 P1 · 运营后台覆盖不全：视频 / 项目 / 学习路径改了前端不同步

- **现象**：后台能管理轮播图、学习方向、菜单、**课程**（这些前端读数据库表，改了即时生效）；但**视频、实战项目、学习路径**后台改了**前端看不到变化**。
- **根因**：前端读的是 **JSON 数据文件**（`data/processed/videos.json` / `projects.json` / `learning_paths.json`），后台管理的是**数据库表**——两套数据源，改库不影响读文件的前端。
- **已核实**：`videos`/`projects`/`learning_paths` 数据库表与对应 JSON 文件 **id 完全一致**（各 24/5/4 条），数据同源 → 迁移成读数据库是**低风险**的。
- **待办（方向 A）**：把视频/项目/路径改为数据库驱动，使后台能真正管理并在前端生效。学习路径较特殊（含动态生成 + per-user 进度合并），需单独处理。

### 🟠 P1 · 后台"作业复核 / 退费复核"页面加载失败（待查）

- **现象**：登录后台后点左侧「作业复核」「退费复核」，主区域显示"加载失败"。
- **已核实**：对应接口本身**正常**（手动带管理员 token 调用均返回 200 与数据：作业复核有提交记录、退费复核有待放行记录），数据与接口都存在。
- **结论**：问题发生在**前端页面加载/渲染环节**（页面 `renderHomework` / `renderRefundReview` 或其请求链路），非数据缺失。需进一步断点/看 Network 定位（可能为 401 误判、请求路径、或页面 JS 异常）。
- **影响**：后台核心的"人工复核"运营能力当前无法在界面上使用。


### 🟡 P2 · 后台无"用户权限 / 试用管理"，调过期/解锁要改数据库

- **现象**：后台没有管理 `user_access`（试用期）的入口；演示"试用过期锁定"目前只能直接改数据库的 `trial_started_at`。
- **建议**：后台增加一个"权限管理"模块，可对指定用户：查看试用状态 / 调整试用起点 / 手动锁定或解锁。既方便测试，也是运营真实的权限控制能力。

### 🟡 P3 · 缺外部资源（卡在申请/采购，不是代码）

| 项 | 现状 | 需要的 |
|---|---|---|
| 微信支付商户号 | 押金走开发模拟支付；生产未配会拒绝报名 | `WXPAY_MCHID/SERIAL_NO/PRIVATE_KEY/APIV3_KEY/NOTIFY_URL`，申请商户号后联调真实下单/回调/退款 |

| 平台发布审核 | — | 小程序提交审核，附测试账号与功能说明 |
| 订阅消息模板 | `WX_SUB_TEMPLATE_*` 为空占位 | 微信后台申请模板（打卡/作业/学习提醒） |

### 🟡 P4 · 测试可继续加量

## 二、运营后台现状

- **入口**：`/admin`（后端 FastAPI 托管单页 HTML）
- **登录**：管理员账号（`admin_users` 表校验，HMAC/SHA256）
- **已实现的功能**：
  1. **数据看板**：用户总数、押金报名、已退费、累计打卡、社区帖子/回复、视频观看、测评次数、FAQ 条目、学习小组、平均测评分、测评等级分布
  2. **作业复核**：列出作业提交，AI 评分 + 人工改判（通过/未通过）
  3. **退费复核**：达标学员退费申请入队，人工放行/驳回（防刷闭环）
  4. **通用表管理**：按导航分组（首页内容 / 课程内容 / 用户体系 / 答疑管理 / 平台运营），对每张表做增删改查、搜索、JSON 字段编辑、启停开关
- **技术形态**：`backend/routers/admin_panel.html`（610 行单页前端，原生 JS）+ `backend/routers/admin.py`（通用 CRUD + 看板 + 复核接口）

## 三、后台已存在的硬编码（记录，待后续清理）

> 这些都是写死在前端页面或后端配置里的，改配置/业务时容易漏改。

1. **登录框预填账号密码**（`admin_panel.html:110-114`）：`value="admin"` 和 `value="admin123"` 写死 → 默认凭据暴露在页面源码里。
2. **字段中文映射** `FIELD_LABELS`（`admin_panel.html:155-179`）：所有表字段的中文名写死在前端，新增字段需手动补。
3. **导航分组** `GROUP_MAP` / `GROUP_ORDER`（`admin_panel.html:182-190`）：哪些表进哪个分组、"数据看板/复核"等菜单写死。
4. **JSON 字段名单** `isJsonField`（`admin_panel.html:455-459`）：哪些字段按 JSON 编辑，写死列表。
5. **自动字段** `AUTO_FIELDS = ['id','created_at','updated_at']`（`admin_panel.html:453`）：新增/编辑时排除，写死。
6. **作业阶段名** `stageName = {1:...7:...}`（`admin_panel.html:348`）：七阶段中文名写死。
7. **数据看板指标卡**（`admin_panel.html:311-316`）：看板展示哪些数字、叫什么，写死。
8. **后端表配置** `TABLE_CONFIG`（`admin.py:57-80`）：每张表的字段白名单、标签写死在后端。

> 硬编码本身不算 bug，但会造成"改业务时两边不同步"。建议后续把字段映射、分组、表配置统一收口（比如从数据库/配置文件读取），属可优化项，非阻塞。

## 四、运营后台"应该补充"的功能（规划，按优先级）

### 高优先（贴近核心业务/防刷/真实性）

- [ ] **用户权限管理**：查看/调整用户试用状态、手动锁定/解锁、查看押金状态 → 解决"调过期要靠改库"
- [ ] **视频 / 项目 / 学习路径**纳入后台真管理（配合方向 A 数据库驱动）
- [ ] **订单/支付流水查看**：已支付、待支付、退费、交易号（配合真实商户号接入后）
- [ ] **课程章节/作业/测评题库**结构化编辑，而不是裸 JSON 表单

### 中优先（运营效率）

- [ ] **用户搜索/详情**：按昵称/OpenID 查用户，看其学习、测评、押金全貌
- [ ] **数据导出**（CSV/Excel）：用户列表、订单、打卡等
- [ ] **数据看板增强**：趋势图（按日/周）、完课漏斗、留存、活跃；不只看静态数字
- [ ] **多管理员 / 角色权限**（超管 / 运营 / 只读），登录凭据不硬编码

### 低优先 / 远期

- [ ] **推广与营销**：邀请码/优惠、限时活动配置
- [ ] **消息推送**：对接订阅消息模板，后台可发学习提醒/通知
- [ ] **操作日志**：记录谁在后台改了什么（合规/追踪）
- [ ] **站内公告**：给用户端发公告/轮播之外的通知
- [ ] **沙箱/模拟支付开关**可视化，便于演示与测试
